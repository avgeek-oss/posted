# Posted v1 requirements and evidence

## Product scope

Posted saves drafts and publishes text, image and video posts for X, LinkedIn, Bluesky and Threads. Each installation has a team, human members and team-owned social connections. Multiple accounts from each provider are supported.

## Delivery semantics

One group represents a posting request. The team-scoped request key is bound permanently to a content hash. Reusing a key with different content returns conflict. Every chosen connection receives one delivery record. Posted reports scheduled, publishing, published, failed, partial and uncertain outcomes truthfully. Worker claims use database leases; leases never authorize a second publish after an external request may already have reached a provider.

## External verification

Provider application credentials and approved scopes are operator configuration. Local contract and integration tests do not establish that a real provider application is approved or that a real post was published. Those gates must remain explicit when reporting readiness.

## Team drafts

The Posts sidebar section orders Drafts, Scheduled Posts and Post History, with the same order in mobile navigation.

Save as draft appears as a secondary action before the publishing button group on desktop and mobile. Draft saving permits empty content, no accounts, disconnected accounts and text exceeding provider limits. Drafts preserve master text, account overrides, selected accounts and ordered images. They use a separate database table and never create delivery jobs. The Drafts sidebar entry opens a shared responsive table with pagination outside the table, edit/view actions and confirmed deletion. Publishing still validates every target and atomically marks the source draft as converted; failed validation leaves it intact. Version checks prevent stale overwrites and request keys make retries safe. The same draft read/save/delete operations are available through REST and MCP within current permissions.

## Delivery set attribution

Delivery details show Requested and Scheduled for in the shared Attributes card above the per-account delivery table. Both timestamps use the current user's date, time and time-zone preferences.

Scheduled Posts and Post History include Posted by, showing the last editor's shared avatar and name. Creation, successful content/schedule changes and cancellation persist the authenticated human responsible, including REST and MCP callers. Failed requests, idempotent retries and background delivery work do not transfer attribution. The response contains a user ID, name and avatar URL, without exposing an email address for this column. Untouched legacy sets use their creator; previously edited sets show Not recorded until their next successful save because the previous editor was not stored.

Drafts include Drafted by with the last successful saver’s shared avatar and name. The API records the authenticated actor in the same transaction as the save. Replayed requests and rejected edits preserve attribution. Untouched legacy drafts use their creator; historically edited drafts show Not recorded until saved again.

The Scheduled Posts and Drafts sidebar entries show team-wide totals through the shared sidebar badge contract, including zero after loading. Scheduled totals count sets with at least one scheduled, preparing or publishing delivery, matching the list. Draft totals exclude converted drafts and are independent of pagination. Successful browser mutations refresh the badges immediately, with five-second foreground polling for worker, REST and MCP changes.

## Image and video media

Single images in the live preview preserve their proportions within a 192 px maximum height and 320 px maximum width, shrinking further to fit the available card width.

Preview text uses its natural content height, followed by a 12 px gap before media. Short text does not reserve blank space above images.

The composer uploads JPEG, PNG and WebP images or MP4/MOV videos through the shared FileUpload control. It displays native inline video controls in the media strip and social preview, preserves ordering, and saves media in drafts and schedules. Images retain a 20 MiB upload bound. Video uploads are capped at 100 MiB and normalized asynchronously to H.264/AAC MP4, at up to 1280×720 with metadata removed. Original files remain private. Processing must finish before scheduling.

Initial video duration bounds are 3–140 seconds for X, 3–180 seconds for Bluesky, 3–300 seconds for Threads and 3–1800 seconds for LinkedIn. X, Bluesky and LinkedIn accept images or the first prioritized video. Threads can use the first 20 media items in mixed carousels. Incompatible media combinations or durations appear in account error badges and are rejected by REST/MCP before queueing. Provider processing finishes during preparation, before the durable publishing boundary.

Provider protocol references: [X media upload](https://docs.x.com/x-api/media/initialize-media-upload), [LinkedIn Videos API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/videos-api), [Bluesky's multipart video client](https://github.com/bluesky-social/social-app/blob/main/src/lib/media/video/multipart/upload.ts), and [Meta's Threads collection](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api). Duration bounds are conservative application limits; account quotas and access are still enforced by providers.
