---
title: "Upgrades"
description: "Replace all three images together after a tested backup."
icon: "package"
---

Choose a published GitHub release and read its release notes. Verify the image references, platform and version. Take a [tested backup](/backup) before changing an installation.

<Steps>
  <Step title="Stop writes and deliveries">
    Use a maintenance window. Stop API and worker and review in-flight or
    uncertain deliveries. Keep users from editing during the snapshot.
  </Step>
  <Step title="Back up the installation">
    Retain PostgreSQL, the stable secret, private configuration and media.
    Record the old version and image references.
  </Step>
  <Step title="Download the new release files">
    Replace `docker-compose.yml` and any release-supplied overlays you use with
    files from the same GitHub release. Keep your existing `.env`. The Compose
    files select matching API, worker and UI versions. Pull the new images.
  </Step>
  <Step title="Start and verify">
    Start Compose. The API migrates before readiness and the worker waits for
    API health. Check all three containers, public origins, sign-in, an existing
    draft and its media.
  </Step>
</Steps>

```sh
docker compose pull
docker compose up -d
docker compose ps
```

Use the same Compose overlays as the original installation. If a migration or startup fails, keep the worker stopped and diagnose the error. Restore a tested snapshot and matching version if recovery requires rollback. Do not mutate migration checksums or reset delivery state to make the upgrade appear successful.

For Towbar, update API, worker and UI to the same release in your deployment repository. Keep the existing datastore and runtime values. Deploy the API first, then the worker and UI, and verify the installation before reopening writes.
